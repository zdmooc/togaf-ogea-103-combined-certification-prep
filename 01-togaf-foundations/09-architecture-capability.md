# 09 — Architecture Capability

## 1. Definition

**Architecture Capability** is the ability of an enterprise to perform Enterprise Architecture effectively and sustainably.

It includes much more than having architects on an organization chart. A real Architecture Capability requires people, skills, governance, processes, roles, principles, repository structures, tools and decision rights that allow architecture work to be performed consistently.

The central question is:

**How is the enterprise organized so that architecture can actually work?**

---

## 2. Why an Architecture Capability is necessary

Imagine that MayaBank hires excellent architects but does not define:

- who approves architectures ;
- which standards apply ;
- how projects request review ;
- how exceptions are handled ;
- where architecture assets are stored ;
- who owns principles ;
- which artifacts are mandatory ;
- how architecture connects to delivery.

The result will still be inconsistent.

Architecture Capability creates the operating system of the architecture practice.

---

## 3. Main elements of an Architecture Capability

A mature capability usually needs clarity around several areas.

### Organization

Where does the architecture function sit?

Examples:

- central enterprise architecture team ;
- federated domain architects ;
- solution architects embedded in delivery ;
- architecture community of practice.

TOGAF does not force one organization model.

### Roles and responsibilities

Examples:

- Chief/Lead Architect ;
- Enterprise Architect ;
- Domain Architect ;
- Solution Architect ;
- Architecture Board members ;
- business stakeholders ;
- governance participants.

The important point is clear accountability.

### Skills

Architecture capability requires more than technical expertise.

Skills may include:

- stakeholder management ;
- modeling ;
- business analysis ;
- technology knowledge ;
- governance ;
- facilitation ;
- communication ;
- risk reasoning.

### Methods and processes

The organization configures how TOGAF will actually be used.

Questions:

- what phases/steps are mandatory?
- what can be tailored?
- what reviews exist?
- which deliverables are required?
- how does architecture interact with Agile/product delivery?

### Principles and standards

The capability maintains the decision rules and standards that guide architecture.

### Repository and tools

Architects need trusted places to create, store and retrieve architecture information.

### Governance

The organization needs decision rights, review mechanisms and escalation paths.

---

## 4. Preliminary Phase connection

The **Preliminary Phase** is where the enterprise prepares or improves the Architecture Capability before undertaking a specific architecture development cycle.

The Preliminary Phase asks questions such as:

- What is the enterprise context?
- What architecture framework will we use?
- How must TOGAF be tailored?
- What principles exist?
- What governance exists?
- What roles and responsibilities are required?
- What tools/repository are available?

This is why Preliminary is different from Phase A.

---

## 5. Preliminary vs Phase A

This distinction is fundamental.

### Preliminary Phase

Focus:

**Prepare the architecture practice.**

Typical subjects:

- Architecture Capability ;
- framework tailoring ;
- governance ;
- organization ;
- principles ;
- tools/repository ;
- enterprise context.

### Phase A — Architecture Vision

Focus:

**Start and frame a specific architecture engagement.**

Typical subjects:

- stakeholders ;
- business drivers ;
- scope ;
- Architecture Vision ;
- value proposition ;
- Statement of Architecture Work ;
- initial risks.

### Memory aid

**Preliminary = prepare the machine.**

**Phase A = start the mission.**

---

## 6. Architecture Board

An **Architecture Board** is a governance body that supports architecture oversight and decision-making.

Depending on the enterprise, it can:

- review architecture ;
- enforce principles and standards ;
- resolve conflicts ;
- approve exceptions ;
- ensure consistency ;
- provide escalation.

Do not confuse Architecture Board with Architecture Team.

### Architecture Team

Creates/analyzes architecture.

### Architecture Board

Provides governance/oversight.

The same individuals may sometimes participate in both, but the functions are different.

---

## 7. Architecture Governance

Architecture Capability requires **Architecture Governance**.

Governance answers questions such as:

- who has authority to decide?
- what must be reviewed?
- what does compliance mean?
- how are deviations handled?
- who accepts architectural risk?
- how is implementation monitored?

Without governance, principles become recommendations with no operational effect.

---

## 8. Tailoring the framework

TOGAF is designed to be configured.

The enterprise may tailor:

- terminology ;
- process steps ;
- required artifacts ;
- governance gates ;
- integration with project/product methods ;
- levels of architecture ;
- repository model.

### Example

MayaBank uses product teams and quarterly architecture reviews.

Instead of forcing a large document at each phase, the configured practice may require:

- specific architecture decision records ;
- capability maps ;
- target views ;
- requirements traceability ;
- roadmap ;
- compliance checkpoints.

The TOGAF logic remains, while the delivery format is tailored.

---

## 9. Capability maturity

An Architecture Capability can be more or less mature.

### Low maturity

- architecture depends on individuals ;
- inconsistent templates ;
- unclear standards ;
- no repository discipline ;
- governance happens late ;
- architecture reviews are political/escalatory.

### Higher maturity

- roles and decision rights are clear ;
- stakeholders know when to engage architects ;
- reusable assets are discoverable ;
- standards are current ;
- exceptions are traceable ;
- architecture is integrated with planning and delivery.

Maturity should not mean bureaucracy. A mature capability can be lightweight and fast if responsibilities and information flows are clear.

---

## 10. Architecture Capability and enterprise change

The capability itself can need change.

Examples:

- company moves from projects to products ;
- cloud adoption changes technology governance ;
- new regulations require stronger evidence ;
- merger creates duplicated architecture teams ;
- AI platform introduces new governance needs.

The architecture practice must therefore evolve, just like the architectures it governs.

---

## 11. MayaBank example

Before starting the Payment Modernization ADM cycle, MayaBank discovers:

- no common definition of Architecture Review ;
- separate standards maintained by infrastructure and applications ;
- no owner for payment-domain architecture ;
- exceptions tracked in email ;
- no common repository.

The Preliminary Phase therefore establishes:

1. a federated Architecture Capability ;
2. Payment Domain Architect responsibility ;
3. an Architecture Board ;
4. common principles ;
5. minimum architecture artifacts ;
6. repository structure ;
7. governance workflow ;
8. exception process.

Only then is the specific payment transformation properly initiated in Phase A.

---

## 12. Architecture Capability and repository

The Architecture Repository contains an area supporting the Architecture Capability.

This can capture:

- organizational structure ;
- roles ;
- governance processes ;
- skill information ;
- method configuration.

This does not mean the Architecture Capability *is* the repository. The repository stores information about the capability; the capability is the real organizational ability to practice architecture.

---

## 13. Architecture Capability vs Architecture

Another important distinction:

### Architecture Capability

The enterprise’s ability to conduct architecture work.

### Architecture

A description/design of a particular enterprise scope or system of interest.

Example:

- MayaBank Architecture Capability defines how architecture is done.
- MayaBank Payment Target Architecture describes the payment future state.

---

## 14. Common mistakes

1. Treating Architecture Capability as a team name.
2. Assuming hiring architects is enough.
3. Creating governance without clear decision rights.
4. Copying TOGAF processes without tailoring.
5. Building a repository without ownership and lifecycle management.
6. Confusing Architecture Board with Architecture Team.
7. Starting Phase A before the architecture practice is sufficiently prepared.
8. Believing the Preliminary Phase happens only once forever.

---

## 15. OGEA-103 exam traps

### Trap 1
Scenario asks to establish governance, principles, roles and framework before a new architecture effort.

→ **Preliminary Phase**.

### Trap 2
Scenario asks to identify stakeholders and agree scope for a specific transformation.

→ **Phase A**, not Preliminary.

### Trap 3
Question asks who performs oversight and resolves architecture governance issues.

→ likely **Architecture Board** rather than Architecture Team.

### Trap 4
TOGAF must be followed identically in every enterprise.

→ false; it is configured/tailored.

## 16. Foundation questions

### Q1
What is Architecture Capability?

**Answer:** the enterprise ability to perform and govern Enterprise Architecture effectively.

### Q2
Which phase establishes or improves the Architecture Capability?

**Answer:** Preliminary Phase.

### Q3
What is the main difference between Preliminary and Phase A?

**Answer:** Preliminary prepares the architecture practice; Phase A initiates and frames a specific architecture engagement.

### Q4
Architecture Board vs Architecture Team?

**Answer:** the Board provides governance/oversight; the Team performs architecture work.

## 17. Practitioner mini-scenario

A new division joins MayaBank after an acquisition. It uses different architecture standards, templates and governance. A transformation project is about to start immediately.

The strongest TOGAF logic is first to address the architecture capability: harmonize or tailor the framework, define governance, roles, principles and repository expectations. Starting detailed Business Architecture without this preparation risks inconsistent work.

## 19. Interview question

**Question:** How would you establish an architecture practice in a new organization?

**Simple answer:**

I would start by understanding the enterprise context, defining architecture roles and governance, reviewing principles and standards, establishing a repository, and tailoring the architecture method to the delivery model. That is close to the purpose of the TOGAF Preliminary Phase.

## 20. Key points to remember

**Architecture Capability = People + Skills + Roles + Method + Principles + Repository + Governance + Tools.**

And the critical comparison:

**Preliminary = prepare the architecture practice.**

**Phase A = launch a specific architecture effort.**
