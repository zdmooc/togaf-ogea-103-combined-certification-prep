# Practitioner — Supporting the ADM Work

## 1. Ce que couvre ce thème

“Supporting the ADM Work” regroupe les pratiques qui rendent l’ADM réellement exploitable : information, governance, repositories, reuse, techniques, architecture capability, risk, security, communication et coordination.

Au Practitioner, il faut reconnaître le mécanisme de support adapté au problème.

## 2. Architecture Repository

Utilise le Repository pour stocker et réutiliser :

- architectures ;
- patterns ;
- standards ;
- principles ;
- models ;
- governance records ;
- reference material.

### Scénario

Une équipe recrée un pattern d’API déjà validé trois fois ailleurs.

Bonne réponse : rechercher et réutiliser les assets existants dans le Repository plutôt que réinventer.

## 3. Enterprise Continuum

Le Continuum aide à classifier et comprendre la progression d’assets plus génériques vers des solutions plus spécifiques.

Piège : Repository = stockage ; Continuum = classification/navigation conceptuelle.

## 4. Architecture Capability

Si les équipes ne savent pas :

- qui décide ;
- quels standards appliquer ;
- comment documenter ;
- où stocker les artifacts ;

le problème peut être la capability d’architecture elle-même.

## 5. Governance support

Architecture Board, Contracts, Compliance Reviews et exception process soutiennent l’ADM en rendant les décisions exécutables et contrôlables.

## 6. Risk Management

Le risque doit être identifié, évalué, traité et suivi.

Une option Practitioner qui ignore un risque connu au motif qu’un projet est urgent est généralement faible.

## 7. Security as cross-cutting concern

Security influence plusieurs phases et ne doit pas être repoussée uniquement à la Technology Architecture.

## 8. Business Scenarios

Utiles lorsque le besoin est vague et doit être transformé en exigences significatives.

## 9. Capability-Based Planning

Utile pour raisonner à partir de ce que l’entreprise doit être capable de faire, au-delà des projets ou systèmes actuels.

## 10. Gap Analysis

Utile pour comparer Baseline et Target et produire la matière nécessaire à la transformation.

## 11. Interoperability

Important lorsque plusieurs systèmes, organisations ou partenaires doivent fonctionner ensemble.

## 12. Transformation Readiness

Une bonne target architecture ne suffit pas si l’organisation n’est pas prête à absorber le changement.

## 13. Communication support

Le Practitioner doit toujours adapter :

- View ;
- Viewpoint ;
- niveau de détail ;
- message ;
- forum de décision.

## 14. Scenario map

| Problème | Support TOGAF probable |
|---|---|
| besoin métier vague | Business Scenario |
| architecture existante réutilisable | Repository |
| classement d’assets | Enterprise Continuum |
| conflit stakeholder | Stakeholder Management + governance |
| cible vs existant | Gap Analysis |
| changement difficile à absorber | Readiness |
| risque critique | Risk Management |
| conformité delivery | Compliance Review |
| problème de rôles/processus EA | Architecture Capability |

## 15. MayaBank — scénario intégré

MayaBank lance plusieurs programmes de paiement. Chaque programme produit ses propres standards, duplique les patterns et sollicite le comité pour des décisions déjà prises ailleurs.

La meilleure réponse n’est pas d’ajouter encore un comité. Il faut renforcer la capability : Repository commun, standards, reuse, gouvernance, responsabilités et mécanismes de décision cohérents.

## 16. Pièges Practitioner

- technique ≠ phase ;
- repository ≠ continuum ;
- governance ≠ documentation ;
- security ≠ uniquement Phase D ;
- readiness ≠ architecture correctness ;
- support ADM ≠ activité secondaire facultative.

## 17. English for Architects

> I support the ADM with reusable architecture assets, governance mechanisms, risk management, stakeholder engagement, and the appropriate architecture techniques.
