# Architecture Content — Questions 263 à 300

## Q263 — Content Framework
L'Architecture Content Framework sert principalement à :
A. Exécuter les composants décrits dans la Technology Architecture cible
B. Remplacer l'ADM
C. Structurer les types de contenu produits par le travail d'architecture
D. Définir les critères de conformité des implémentations
**Réponse : C.** Il organise deliverables, artifacts et building blocks. A/B/D sont hors sujet.
**Distracteur D :** La conformité est nécessaire, mais le Content Framework structure avant tout les contenus et relations architecturales.
**Mapping : Architecture Content — Content Framework.**

## Q264 — Content categories
Quelles catégories sont centrales dans l'Architecture Content Framework ?
A. Architecture Vision, Architecture Roadmap et Architecture Contract
B. Sprints, Stories, Epics uniquement
C. CPU, RAM, Disk uniquement
D. Deliverables, Artifacts, Building Blocks
**Réponse : D.** C'est la triade structurante de l'Architecture Content Framework : Deliverables, Artifacts et Building Blocks.
**Distracteur A :** Ce sont des exemples de deliverables, pas les trois catégories générales.
**Mapping : Architecture Content — Content Framework.**

## Q265 — Deliverable
Un deliverable est :
A. Un produit de travail formel soumis à review/approval
B. Un unique diagramme indépendamment des conditions d'acceptation du livrable
C. Un building block de solution nécessairement déployé avant la revue
D. Un viewpoint
**Réponse : A.** Un deliverable peut regrouper plusieurs artifacts. B/C/D sont faux.
**Mapping : Architecture Content — Deliverables.**

## Q266 — Artifact
Un artifact est :
A. Un composant de solution réutilisable déployé pour réaliser une capability métier
B. Une représentation architecturale d'un aspect de l'architecture
C. Un produit de travail contractuel rassemblant les vues et exigences de la cible
D. Une phase de développement d'architecture au sein du cycle ADM
**Réponse : B.** Catalogs, matrices et diagrams sont des artifacts.
**Distracteur D :** Un deliverable peut rassembler plusieurs artifacts ; les deux notions ne sont pas synonymes.
**Mapping : Architecture Content — Artifacts.**

## Q267 — Building Block
Un building block est :
A. Un document formel soumis à l'approbation de l'Architecture Board pendant un jalon ADM
B. Une représentation graphique dont la convention de construction est définie par un viewpoint
C. Un élément potentiellement réutilisable qui décrit ou réalise une capacité architecturale
D. Une requirement vérifiable indiquant la contrainte à satisfaire par une solution donnée
**Réponse : C.** Les building blocks structurent les architectures et solutions.
**Distracteur A :** La vue est une représentation des building blocks, pas nécessairement un block elle-même.
**Mapping : Architecture Content — Building Blocks.**

## Q268 — Deliverable contains Artifact

**Réponse : D.** Les artifacts sont des éléments de contenu pouvant être assemblés dans des deliverables.
**Mapping : Architecture Content — Deliverable vs Artifact.**

Quel énoncé est le plus juste ?

## Q270 — Triad synthesis

## Q271 — Catalog
Un catalog est principalement :
A. Une matrice décrivant les correspondances entre plusieurs types d'éléments d'architecture
B. Un diagramme représentant graphiquement les interfaces et relations entre services
C. Une liste structurée d'éléments d'architecture
D. Un deliverable approuvé décrivant formellement un ensemble de vues et exigences
**Réponse : C.** Un catalog inventorie/classifie des éléments.
**Mapping : Architecture Content — Catalogs.**

## Q272 — Matrix
Une matrix sert surtout à :
A. Lister les éléments d'un domaine sans établir leurs liens avec d'autres éléments
B. Documenter les engagements des implementers dans le contrat d'architecture
C. Représenter un état complet de l'Architecture Landscape à un jalon cible
D. Montrer des relations entre deux ensembles d'éléments
**Réponse : D.** La matrix met en évidence des correspondances et dépendances.
**Mapping : Architecture Content — Matrices.**

## Q273 — Diagram
Un diagram sert principalement à :
A. Visualiser des éléments et relations dans une représentation graphique
B. Inventorier des éléments architecturaux dans une liste structurée sans représenter leurs relations
C. Montrer des correspondances entre deux ensembles d'éléments dans un tableau croisé
D. Définir les conventions de construction et d'interprétation d'une view
**Réponse : A.** Un diagram représente graphiquement éléments et relations. B correspond plutôt à un catalog, C à une matrix et D à un viewpoint ; ces représentations ne sont pas interchangeables.
**Distracteur D :** Cette fonction concerne une Architecture Requirements Specification ; le diagramme représente graphiquement un aspect.
**Mapping : Architecture Content — Diagrams.**

## Q274 — Catalog vs Matrix
Quelle distinction est correcte ?
A. Catalog et Matrix servent tous deux à lister des éléments, sans différence sur la représentation des relations
B. Catalog = liste structurée ; Matrix = relations entre ensembles
C. Le Catalog montre les relations entre deux ensembles tandis que la Matrix ne décrit qu'une liste d'éléments
D. Une Matrix est un deliverable formel de gouvernance tandis qu'un Catalog est toujours une Architecture View
**Réponse : B.** Un Catalog inventorie des éléments ; une Matrix met en évidence des correspondances entre ensembles. A gomme la distinction, C l'inverse, D confond artifacts, deliverables et views.
**Mapping : Architecture Content — Catalog vs Matrix.**

## Q275 — Matrix vs Diagram
Quelle phrase est la plus juste ?
A. Un diagram est un deliverable approuvé ; la matrix est toujours un SBB déployé en production
B. Une matrix est exclusivement un calendrier de migration ; un diagram est nécessairement un Architecture Contract
C. Une matrix formalise des correspondances ; un diagram met en scène visuellement des éléments/relations
D. Une matrix spécifie la convention du viewpoint ; le diagram ne peut représenter que le niveau technique
**Réponse : C.** Les deux sont des artifacts mais répondent à des besoins de représentation différents.
**Mapping : Architecture Content — Matrix vs Diagram.**

## Q276 — Viewpoint
Un viewpoint définit :
A. Les composants représentés dans une architecture view approuvée à un jalon du projet
B. Les décisions et exceptions de l'Architecture Board enregistrées dans le Governance Repository
C. Les instances de capabilities et services métiers définies dans un Architecture Metamodel
D. Les conventions pour construire une view répondant à certains concerns
**Réponse : D.** Viewpoint = manière/convention ; View = représentation produite.
**Mapping : Architecture Content — Views/Viewpoints.**

## Q277 — View
Une view est :
A. La représentation concrète construite selon un viewpoint
B. Une convention de construction et d'interprétation des représentations d'architecture
C. Un composant concret permettant de réaliser un service de la Target Architecture
D. Un ensemble d'engagements d'implémentation formalisés entre parties prenantes
**Réponse : A.** B décrit le viewpoint ; C/D sont autres concepts.
**Mapping : Architecture Content — Views/Viewpoints.**

## Q278 — Concern to View

## Q279 — Viewpoint reusable
Pourquoi un viewpoint peut-il être réutilisable ?
A. Parce qu'une View représente toujours le même SBB pour toutes les organisations

## Q300 — Content synthesis

A. Stakeholder → Requirement → Architecture Contract → Compliance Review, sans représenter les views
