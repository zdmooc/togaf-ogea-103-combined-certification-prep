# Introduction to Architecture Governance — Questions 241 à 262

## Q241 — Architecture Governance
Architecture Governance sert principalement à :
A. Organiser décisions, conformité, responsabilités et exceptions d'architecture  B. Écrire tout le code  C. Remplacer la stratégie métier  D. Supprimer les stakeholders
**Réponse : A.** La gouvernance rend les décisions explicites, appliquées et traçables. B/C/D sont faux.
**Mapping : Architecture Governance — Fundamentals.**

## Q242 — Governance vs project management
Quelle distinction est correcte ?
A. Architecture Governance veille à la conformité et aux décisions d'architecture ; Project Governance pilote notamment coûts/délais/risques projet  B. Elles sont synonymes  C. Architecture Governance gère uniquement le budget  D. Project Governance définit seule la Target Architecture
**Réponse : A.** Les deux se coordonnent mais ont des objets différents.
**Mapping : Architecture Governance — Governance boundaries.**

## Q243 — Architecture Board
Le rôle principal d'un Architecture Board est :
A. Arbitrer et gouverner les décisions d'architecture significatives  B. Développer tout le code  C. Exploiter les serveurs  D. Remplacer toutes les équipes projet
**Réponse : A.** Le Board fournit un forum de décision et de conformité. B/C/D sont opérationnels ou excessifs.
**Mapping : Architecture Governance — Architecture Board.**

## Q244 — Board decision
Quand un Architecture Board est-il particulièrement utile ?
A. Lorsqu'une décision transverse ou une exception importante nécessite arbitrage  B. Pour chaque correction orthographique  C. Pour toutes les tâches d'exploitation  D. Pour supprimer les requirements
**Réponse : A.** Le Board doit se concentrer sur les décisions architecturales significatives.
**Mapping : Architecture Governance — Architecture Board.**

## Q245 — Board composition
Un Architecture Board efficace doit idéalement :
A. Avoir l'autorité et la représentation nécessaires aux décisions qu'il porte  B. Être composé uniquement de développeurs d'un seul produit  C. Ne jamais inclure le métier  D. Ne disposer d'aucune règle de décision
**Réponse : A.** Sa composition dépend du scope mais doit rendre les arbitrages crédibles et exécutoires.
**Mapping : Architecture Governance — Architecture Board.**

## Q246 — Architecture Contract
Un Architecture Contract est principalement :
A. Un accord formalisant les responsabilités et attentes entre parties autour de l'architecture  B. Un diagramme réseau  C. Une Business Capability  D. Une Transition Architecture
**Réponse : A.** Il explicite les engagements de conformité et collaboration. B/C/D sont d'autres objets.
**Mapping : Architecture Governance — Architecture Contract.**

## Q247 — Contract in implementation
Pendant Phase G, l'Architecture Contract aide à :
A. Clarifier ce que les équipes d'implémentation doivent respecter et fournir comme preuves  B. Redéfinir la Business Architecture  C. Remplacer le code  D. Supprimer les reviews
**Réponse : A.** Le contrat soutient la gouvernance de mise en œuvre.
**Mapping : Architecture Governance — Architecture Contract.**

## Q248 — Contract vs Architecture Vision
Quelle différence est correcte ?
A. La Vision aligne sur la direction cible ; le Contract formalise des engagements de gouvernance entre parties  B. Ils sont identiques  C. Le Contract définit toujours la Target Data Architecture  D. La Vision est un waiver
**Réponse : A.** Les deux ont des finalités différentes.
**Mapping : Architecture Governance — Contract vs Vision.**

## Q249 — Compliance Review
Une Architecture Compliance Review sert à :
A. Comparer une implémentation ou solution aux requirements et décisions d'architecture approuvées  B. Créer le scope  C. Définir les business goals  D. Remplacer Phase E
**Réponse : A.** Elle vérifie l'alignement effectif.
**Mapping : Architecture Governance — Compliance.**

## Q250 — Compliance evidence
Quel élément est utile lors d'une Compliance Review ?
A. Requirements, decisions, architecture contracts et preuves d'implémentation  B. Uniquement le nom du projet  C. Uniquement le budget  D. Uniquement les impressions du sponsor
**Réponse : A.** Une review doit être factuelle et traçable.
**Mapping : Architecture Governance — Compliance.**

## Q251 — Non-compliance
Une review découvre un écart important. Quelle action est la plus cohérente ?
A. Enregistrer l'écart, évaluer son impact et décider correction ou exception via governance  B. Le cacher  C. Déclarer automatiquement l'architecture invalide sans analyse  D. Supprimer le requirement localement
**Réponse : A.** La gouvernance traite explicitement les écarts.
**Mapping : Architecture Governance — Compliance/Exception.**

## Q252 — Deviation
Une deviation est :
A. Un écart par rapport à une architecture, standard ou requirement approuvé  B. Une phase ADM  C. Un stakeholder  D. Un building block
**Réponse : A.** Elle décrit la non-conformité constatée.
**Mapping : Architecture Governance — Deviations.**

## Q253 — Exception
Une exception/waiver est :
A. Une autorisation gouvernée de déroger à une règle sous conditions  B. Toute erreur non détectée  C. Une Target Architecture  D. Un business goal
**Réponse : A.** Une exception est explicitement décidée, documentée et souvent limitée.
**Mapping : Architecture Governance — Exceptions.**

## Q254 — Exception conditions
Une bonne exception doit idéalement préciser :
A. Rationale, scope, risques, owner, durée/conditions et actions futures  B. Seulement « approuvé »  C. Aucun responsable  D. Aucune date de revue
**Réponse : A.** Une exception gouvernée doit être traçable et contrôlable.
**Mapping : Architecture Governance — Exceptions.**

## Q255 — Temporary waiver
Pourquoi une exception temporaire peut-elle être préférable à modifier immédiatement le standard ?
A. Parce qu'un cas local ne justifie pas forcément de changer une règle globale  B. Parce que les standards ne changent jamais  C. Pour éviter toute analyse  D. Pour supprimer la gouvernance
**Réponse : A.** Le waiver permet de gérer un cas particulier sans généraliser trop vite.
**Mapping : Architecture Governance — Exceptions.**

## Q256 — Governance log
Pourquoi tenir un Governance Log ?
A. Pour tracer décisions, reviews, exceptions et responsabilités  B. Pour stocker uniquement le code  C. Pour remplacer le Repository  D. Pour supprimer les audits
**Réponse : A.** Le log fournit une mémoire de gouvernance.
**Mapping : Architecture Governance — Governance Log.**

## Q257 — Escalation
Une équipe ne peut résoudre un conflit architectural local. Que faire ?
A. Escalader selon le modèle de governance prévu  B. Décider secrètement  C. Ignorer le conflit  D. Supprimer le stakeholder concerné
**Réponse : A.** L'escalation vers l'autorité appropriée protège cohérence et traçabilité.
**Mapping : Architecture Governance — Escalation.**

## Q258 — Governance principles
Pourquoi des principles approuvés sont-ils importants pour la governance ?
A. Ils fournissent des critères durables pour guider et arbitrer les décisions  B. Ils remplacent tous les requirements  C. Ils éliminent le besoin de jugement  D. Ils ne servent qu'en Preliminary
**Réponse : A.** Les principles soutiennent les décisions tout au long du cycle.
**Mapping : Architecture Governance — Principles.**

## Q259 — Governance in G
Quelle phase est la plus directement associée à la governance de l'implémentation ?
A. G  B. B  C. C  D. F
**Réponse : A.** Phase G = Implementation Governance.
**Mapping : Architecture Governance — Phase G.**

## Q260 — Governance and H
En Phase H, la governance sert notamment à :
A. Décider comment répondre aux changements et s'il faut un nouveau cycle  B. Déployer sans analyse  C. Ignorer les drivers  D. Supprimer le Board
**Réponse : A.** H gouverne l'évolution de l'architecture.
**Mapping : Architecture Governance — Phase H.**

## Q261 — Best governance behavior
Quel comportement est le plus mature ?
A. Rendre les écarts visibles et les traiter selon un processus de décision connu  B. Tolérer des exceptions implicites  C. Modifier les standards sans trace  D. Éviter les compliance reviews
**Réponse : A.** La gouvernance repose sur visibilité, décision et traçabilité.
**Mapping : Architecture Governance — Synthesis.**

## Q262 — Governance synthesis
Quel enchaînement est le plus cohérent ?
A. Principles/requirements → Architecture Contract → implementation → Compliance Review → correction ou exception  B. Exception → aucun requirement → déploiement  C. Compliance Review avant toute architecture  D. Board → suppression de tout delivery
**Réponse : A.** Il relie règles, engagement, implémentation, contrôle et traitement des écarts.
**Mapping : Architecture Governance — Synthesis.**
