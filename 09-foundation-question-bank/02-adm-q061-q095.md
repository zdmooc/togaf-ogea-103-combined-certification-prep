# Introduction to the ADM — Questions 061 à 095

## Q061 — Preliminary
Quel est le but principal de la Preliminary Phase ?
A. Définir la Target Technology Architecture  B. Préparer l'Architecture Capability, la gouvernance et l'adaptation du framework  C. Prioriser les work packages  D. Gouverner l'implémentation
**Réponse : B.** Preliminary prépare la capacité à faire de l'architecture. A relève de D, C de F, D de G.
**Mapping : ADM — Preliminary.**

## Q062 — Preliminary vs A
Quelle question relève surtout de Preliminary ?
A. Quel est le scope du nouvel engagement ?  B. Comment notre organisation pratique-t-elle et gouverne-t-elle l'architecture ?  C. Quelle Target Business Architecture ?  D. Quel ordre de migration ?
**Réponse : B.** Preliminary traite la capacité et le cadre. A est surtout Phase A, C Phase B, D Phase F.
**Mapping : ADM — Preliminary vs Phase A.**

## Q063 — Architecture Capability
Quel résultat est cohérent avec Preliminary ?
A. Un Architecture Board et des rôles clarifiés  B. Un plan de migration détaillé  C. Une conformité de solution déployée  D. Une Target Application Architecture complète
**Réponse : A.** Gouvernance et rôles appartiennent à la capacité d'architecture. B=F, C=G, D=C.
**Mapping : ADM — Preliminary.**

## Q064 — Tailoring en Preliminary
Pourquoi tailor l'ADM en Preliminary ?
A. Pour adapter méthode, gouvernance et livrables au contexte organisationnel  B. Pour supprimer les requirements  C. Pour imposer le même détail partout  D. Pour choisir un fournisseur
**Réponse : A.** Le tailoring rend l'ADM proportionné. B/C/D ne sont pas son objectif.
**Mapping : ADM — Preliminary/Tailoring.**

## Q065 — Request for Architecture Work
Le Request for Architecture Work sert principalement à :
A. Déclencher/formaliser un besoin de travail d'architecture  B. Décrire tous les SBB  C. Clore Phase H  D. Remplacer le Repository
**Réponse : A.** Il initie un engagement. B est trop détaillé, C/D sont faux.
**Mapping : ADM — Preliminary/A.**

## Q066 — Phase A
Le but principal de Phase A est :
A. Détailler toutes les applications  B. Établir l'Architecture Vision, le scope et obtenir l'alignement initial  C. Séquencer les projets  D. Contrôler la conformité du code
**Réponse : B.** Phase A cadre et donne la vision. A=C, C=F, D=G/delivery.
**Mapping : ADM — Phase A.**

## Q067 — Scope en Phase A
Quel élément doit être clarifié très tôt en Phase A ?
A. Le scope  B. Le modèle physique de données final  C. La configuration Kubernetes  D. Les tests de bascule détaillés
**Réponse : A.** Le scope est fondamental pour l'engagement. B/C/D viennent plus tard selon contexte.
**Mapping : ADM — Phase A.**

## Q068 — Stakeholders en A
Pourquoi identifier les stakeholders en Phase A ?
A. Pour comprendre leurs concerns et construire l'alignement  B. Pour éviter les requirements  C. Pour choisir les serveurs  D. Pour supprimer la gouvernance
**Réponse : A.** Les stakeholders conditionnent views, requirements et décisions. B/C/D sont faux.
**Mapping : ADM — Phase A/Stakeholders.**

## Q069 — Architecture Vision
L'Architecture Vision doit être :
A. Un design exhaustif  B. Une représentation de haut niveau de la valeur, du scope et de la direction cible  C. Une liste de tous les artifacts  D. Un runbook
**Réponse : B.** Elle aligne sans détailler toute la cible. A/C sont excessifs ; D est opérationnel.
**Mapping : ADM — Phase A.**

## Q070 — Statement of Architecture Work
Le Statement of Architecture Work sert surtout à :
A. Décrire le travail d'architecture convenu, son scope, approche et gouvernance  B. Lister les incidents  C. Définir uniquement les standards réseau  D. Remplacer l'Architecture Vision
**Réponse : A.** Il formalise l'engagement. B/C/D ne correspondent pas.
**Mapping : ADM — Phase A.**

## Q071 — Business goals
En Phase A, les business goals servent à :
A. Relier l'architecture à la valeur recherchée  B. Sélectionner automatiquement un produit  C. Remplacer les stakeholders  D. Définir le code
**Réponse : A.** Les goals donnent la direction de valeur. B/C/D sont faux.
**Mapping : ADM — Phase A.**

## Q072 — Risk en A
Pourquoi évaluer les risques dès Phase A ?
A. Pour comprendre tôt les obstacles majeurs et l'exposition de la transformation  B. Pour terminer Phase G  C. Pour éviter tout changement  D. Pour choisir le SBB final
**Réponse : A.** Le risque doit influencer scope, vision et gouvernance dès le départ.
**Mapping : ADM — Phase A/Risk.**

## Q073 — A vs B
Quelle distinction est correcte ?
A. A détaille Business Architecture, B crée la vision  B. A cadre/visionne, B développe la Business Architecture  C. A et B sont identiques  D. B ne traite jamais les gaps
**Réponse : B.** A est high-level ; B développe Baseline/Target métier. A/C/D sont faux.
**Mapping : ADM — Phase A vs B.**

## Q074 — Phase B
Phase B traite principalement :
A. Business Architecture  B. Technology Architecture  C. Migration Planning  D. Implementation Governance
**Réponse : A.** B développe l'architecture métier. B/C/D correspondent à D/F/G.
**Mapping : ADM — Phase B.**

## Q075 — Baseline Business
La Baseline Business Architecture décrit :
A. Le fonctionnement métier actuel pertinent  B. Le futur technologique  C. Les work packages  D. Les exceptions de gouvernance
**Réponse : A.** Baseline = current business state. B/C/D sont autres sujets.
**Mapping : ADM — Phase B.**

## Q076 — Target Business
La Target Business Architecture doit surtout refléter :
A. Les capacités/processus/services métier nécessaires pour atteindre les objectifs  B. Les versions de serveurs actuelles  C. Le calendrier détaillé de tests  D. Uniquement les applications
**Réponse : A.** La Target Business exprime le futur fonctionnement métier. B/C/D sont trop techniques ou limités.
**Mapping : ADM — Phase B.**

## Q077 — Gap Analysis en B
Après comparaison Baseline/Target Business, que produit-on notamment ?
A. Des gaps métier  B. Un Architecture Contract final de G  C. Un code source  D. Une certification
**Réponse : A.** La Gap Analysis identifie ce qui doit changer. B/C/D ne sont pas l'output principal.
**Mapping : ADM — Phase B.**

## Q078 — Capability en B
Quel élément est particulièrement pertinent en Business Architecture ?
A. Business Capability  B. Adresse IP d'un serveur  C. Version d'un runtime  D. Modèle physique de stockage
**Réponse : A.** Les capabilities sont centrales au métier. B/C/D relèvent davantage de Technology/Data.
**Mapping : ADM — Phase B.**

## Q079 — B vers C
Un gap métier montre le besoin d'une information nouvelle. Quelle phase est particulièrement concernée ensuite ?
A. Phase C Data  B. Phase G uniquement  C. Phase H uniquement  D. Preliminary
**Réponse : A.** Le besoin informationnel alimente Data Architecture. B/C/D sont trop tardifs ou hors sujet.
**Mapping : ADM — B to C.**

## Q080 — Phase C
Phase C couvre :
A. Business et Technology  B. Data et Application Architectures  C. Opportunities et Migration  D. Governance et Change
**Réponse : B.** Phase C = Information Systems Architectures, Data + Application.
**Mapping : ADM — Phase C.**

## Q081 — Data Architecture
Quel sujet appartient le plus à Phase C Data ?
A. Data ownership et flux d'information  B. Priorisation des projets  C. Architecture Board  D. Conformité d'implémentation
**Réponse : A.** B=F, C=governance/Preliminary, D=G.
**Mapping : ADM — Phase C Data.**

## Q082 — Data Baseline/Target
En Phase C Data, la bonne démarche est :
A. Comprendre la Baseline, définir la Target et identifier les gaps data  B. Choisir directement une base  C. Ignorer les owners  D. Traiter seulement les sauvegardes
**Réponse : A.** Le cycle Baseline→Target→Gap s'applique au domaine Data. B/C/D sont trop étroits.
**Mapping : ADM — Phase C Data.**

## Q083 — Data governance
Pourquoi l'ownership est-il important dans Data Architecture ?
A. Pour clarifier responsabilité, qualité et décisions sur les données  B. Pour remplacer la sécurité  C. Pour supprimer le lifecycle  D. Pour choisir Phase F
**Réponse : A.** L'ownership soutient la gouvernance des données. B/C/D sont faux.
**Mapping : ADM — Phase C Data.**

## Q084 — Data ≠ database
Pourquoi « choisir PostgreSQL » n'est-il pas suffisant pour Data Architecture ?
A. Parce que Data Architecture couvre aussi modèles, ownership, qualité, lifecycle et flux  B. Parce que les bases sont interdites  C. Parce que Phase C ne traite aucune donnée  D. Parce que seul le réseau compte
**Réponse : A.** La Data Architecture est plus large que la technologie de stockage.
**Mapping : ADM — Phase C Data.**

## Q085 — Application Architecture
Phase C Application décrit principalement :
A. Les applications/services applicatifs et leurs interactions  B. Les objectifs stratégiques uniquement  C. Le séquencement de migration  D. Les exceptions au Board

## Q086 — Application services
Quel élément est le plus typique d'une Target Application Architecture ?

## Q087 — Application gap
Une fonctionnalité est dupliquée dans cinq applications et doit être rationalisée. C'est principalement :
A. Un gap Application  B. Un concern uniquement  C. Une Phase H  D. Un Architecture Principle

## Q088 — Data vs Application
