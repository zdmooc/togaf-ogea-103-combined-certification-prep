# Practitioner Scenarios — Implementing the Architecture (Phases E, F, G)

## S031 — Des gaps aux work packages

Les Phases B/C/D sont terminées. MayaBank dispose d’un ensemble de gaps métier, data, application et technology, mais aucune trajectoire concrète n’existe encore.

Quelle action est la meilleure ?

A. Consolider les gaps, identifier les solution building blocks potentiels, work packages et Transition Architectures en Phase E.  
B. Commencer directement les déploiements en Phase G.  
C. Produire immédiatement un planning détaillé de ressources en Phase F sans définir les work packages.  
D. Refaire Phase A.

**Scoring : A=5, C=3, D=1, B=0.**

**Pourquoi A :** Phase E transforme l’architecture cible et ses gaps en options de transformation structurées. C commence trop tôt la priorisation détaillée ; D peut être utile si les drivers ont changé mais ce n’est pas indiqué ; B saute E/F.

**Mapping : Implementing Architecture — Phase E.**

## S032 — E ou F ?

Une équipe a déjà identifié six work packages et deux Transition Architectures. Elle doit maintenant arbitrer coûts, bénéfices, risques, dépendances et calendrier afin de produire un plan d’implémentation priorisé.

Quelle action est la meilleure ?

A. Continuer Phase E et créer encore des work packages.  
B. Entrer en Phase F pour prioriser, séquencer et finaliser l’Implementation and Migration Plan.  
C. Passer directement en Phase H.  
D. Revenir en Phase B pour classer les coûts.

**Scoring : B=5, A=3, D=1, C=0.**

**Pourquoi B :** Phase E structure les options ; Phase F les priorise et les séquence dans un plan de migration. A peut encore affiner E mais ne répond pas au besoin dominant ; D et C sont hors séquence.

## S033 — Big bang ou Transition Architecture ?

La Target suppose le remplacement de trois systèmes critiques. Le programme propose un big bang, mais la banque ne peut tolérer qu’une interruption très courte et doit maintenir certains systèmes legacy pendant douze mois.

Quelle action est la meilleure ?

A. Définir une ou plusieurs Transition Architectures cohérentes permettant la coexistence contrôlée de Baseline et Target.  
B. Maintenir le big bang parce que la Target est déjà approuvée.  
C. Appeler le planning existant « Transition Architecture ».  
D. Reporter la question à Phase H.

**Scoring : A=5, B=3, C=1, D=0.**

**Pourquoi A :** une Transition Architecture décrit un état intermédiaire viable, pas un planning. B peut être simple mais ignore continuité et contraintes ; C confond état architectural et plan ; D arrive après l’implémentation.

**Mapping : Implementing Architecture — Transition Architectures.**

## S034 — Priorité politique contre valeur

En Phase F, un directeur exige que son projet soit lancé en premier. L’analyse montre pourtant qu’un autre work package produit davantage de valeur, réduit un risque majeur et débloque plusieurs dépendances.

Quelle action est la meilleure ?

A. Prioriser selon critères explicites de business value, risk, dependency, cost et readiness, puis faire arbitrer les conflits par la gouvernance appropriée.  
B. Donner automatiquement priorité au directeur le plus influent.  
C. Tirer au sort pour rester neutre.  
D. Lancer tous les work packages simultanément.

**Scoring : A=5, B=3, D=1, C=0.**

**Pourquoi A :** Phase F organise un séquencement défendable et gouverné. B reconnaît le pouvoir d’un stakeholder mais abandonne l’analyse ; D peut être impossible à cause des dépendances ; C n’est pas une méthode de planification.

**Mapping : Implementing Architecture — Phase F / Prioritization.**

## S035 — Dépendance invisible

Le work package « New Payment API » est planifié avant « Identity Federation », alors que la nouvelle API dépend du mécanisme d’identité cible. Le plan a été construit uniquement selon la date souhaitée par le métier.

Quelle action est la meilleure ?

A. Réanalyser les dependencies et ajuster les migration waves pour respecter les prérequis tout en évaluant l’impact métier.  
B. Conserver le planning car le métier l’a demandé.  
C. Supprimer Identity Federation du scope.  
D. Laisser le delivery découvrir la dépendance en Phase G.

**Scoring : A=5, B=3, D=1, C=0.**

**Pourquoi A :** le séquencement doit intégrer dépendances et faisabilité. B préserve un objectif de date mais peut rendre le plan inexécutable ; D reporte un défaut de Phase F ; C modifie le scope sans justification.

**Mapping : Implementing Architecture — Phase F / Dependencies.**

## S036 — Architecture Contract

Les équipes de delivery démarrent l’implémentation. Plusieurs contraintes d’architecture sont connues, mais responsabilités, obligations, critères de conformité et gestion des écarts restent implicites.

Quelle action est la meilleure ?

A. Formaliser les engagements pertinents via un Architecture Contract ou mécanisme équivalent, puis gouverner l’implémentation en Phase G.  
B. Considérer les diagrammes comme suffisants pour contractualiser les responsabilités.  
C. Attendre Phase H pour définir les obligations.  
D. Laisser chaque équipe interpréter les principes librement.

**Scoring : A=5, B=3, D=1, C=0.**

**Pourquoi A :** Phase G a besoin d’engagements et de critères explicites pour gouverner l’implémentation. B apporte une référence mais sans responsabilités claires ; D fragilise la conformité ; C arrive trop tard.

**Mapping : Implementing Architecture — Phase G / Architecture Contract.**

## S037 — Écart découvert pendant le delivery

Une équipe ne peut respecter un standard de messagerie à cause d’une contrainte fournisseur. Elle propose une technologie alternative qui répond aux requirements métier mais s’écarte des standards approuvés.

Quelle action est la meilleure ?

A. Documenter l’écart, analyser son impact et soumettre une deviation/exception à la gouvernance prévue plutôt que le cacher.  
B. Refuser automatiquement toute alternative.  
C. Autoriser l’alternative localement sans trace puisqu’elle fonctionne.  
D. Modifier rétroactivement le standard sans revue.

**Scoring : A=5, B=3, C=1, D=0.**

**Pourquoi A :** la gouvernance doit distinguer non-conformité, exception et changement de standard. B protège la cohérence mais ignore les réalités ; C contourne la gouvernance ; D altère la référence sans décision.

**Mapping : Implementing Architecture — Phase G / Exceptions and Deviations.**

## S038 — Compliance Review

Le programme affirme respecter l’architecture parce qu’il utilise les mêmes produits que la Target. Cependant, plusieurs requirements de disponibilité, sécurité et observabilité n’ont jamais été vérifiées.

Quelle action est la meilleure ?

A. Réaliser une Architecture Compliance Review fondée sur les requirements, principes, building blocks et décisions approuvés, puis traiter les écarts.  
B. Considérer l’utilisation des mêmes produits comme preuve suffisante.  
C. Vérifier seulement la conformité budgétaire.  
D. Attendre les incidents de production pour évaluer la conformité.

**Scoring : A=5, B=3, C=1, D=0.**

**Pourquoi A :** conformité d’architecture ≠ simple identité de produits. B peut indiquer un alignement partiel mais ne couvre pas requirements et behavior ; C est trop étroit ; D remplace la gouvernance proactive par une réaction tardive.

**Mapping : Implementing Architecture — Phase G / Compliance Review.**

## S039 — F ou G ?

Le programme a un Implementation and Migration Plan approuvé. Un changement de budget impose de décaler une migration wave avant que son implémentation commence.

Quelle action est la meilleure ?

A. Réévaluer priorités, dépendances, risques et plan de migration dans le cadre de Phase F/planification, puis mettre à jour les engagements avant Phase G pour la wave concernée.  
B. Traiter le décalage uniquement comme une non-conformité Phase G.  
C. Ignorer le changement puisque le plan est approuvé.  
D. Déclencher automatiquement Phase H.

**Scoring : A=5, B=3, D=1, C=0.**

**Pourquoi A :** tant que la question porte sur séquencement avant implémentation, elle relève principalement de migration planning. B peut être utile si un engagement d’implémentation est déjà violé, mais ce n’est pas le cas dominant ; D est destiné au changement d’architecture en exploitation ; C nie une contrainte réelle.

**Mapping : Implementing Architecture — Phase F vs G.**
