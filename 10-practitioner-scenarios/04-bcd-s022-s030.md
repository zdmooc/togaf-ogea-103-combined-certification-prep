# Practitioner Scenarios — Architecture Development (Phases B, C, D)

## S022 — Capability ou application ?

En Phase B, une équipe affirme que « Payment Validation » est l’application Java existante qui porte ce nom. Le métier veut cependant conserver cette capacité après remplacement de l’application.

Quelle action est la meilleure ?

A. Définir Payment Validation comme business capability indépendante de l’application, puis analyser les applications qui la supportent en Phase C.  
B. Conserver capability et application comme synonymes pour simplifier les modèles.  
C. Traiter uniquement l’application en Phase D.  
D. Attendre Phase G pour définir la capability.

**Scoring : A=5, B=3, C=1, D=0.**

**Pourquoi A :** une capability décrit ce que l’entreprise doit savoir faire ; l’application est un moyen de support. B semble simplifier mais crée un couplage conceptuel ; C mélange domaine Application/Technology ; D arrive trop tard.

**Mapping : Architecture Development — Phase B vs Phase C.**

## S023 — Baseline exhaustive

L’équipe Business Architecture veut documenter chaque processus, rôle, règle et formulaire des vingt dernières années avant de commencer la Target. Le délai estimé est de neuf mois.

Quelle action est la meilleure ?

A. Documenter la Baseline au niveau nécessaire pour comprendre le scope, les impacts et les gaps, puis concentrer l’effort sur la Target.  
B. Accepter l’inventaire exhaustif car TOGAF exige une Baseline complète.  
C. Ne documenter aucune Baseline.  
D. Remplacer l’analyse métier par une liste d’applications.

**Scoring : A=5, B=3, C=1, D=0.**

**Pourquoi A :** le niveau de détail doit être proportionné au besoin. B reconnaît l’importance de la Baseline mais maximise inutilement l’effort ; C perd le point de comparaison ; D confond Business et Application Architecture.

**Mapping : Architecture Development — Baseline / Fit-for-Purpose Detail.**

## S024 — Data Architecture réduite à PostgreSQL

En Phase C Data, le DBA propose de considérer le travail terminé dès que PostgreSQL est choisi. Or les équipes ne savent toujours pas qui possède la donnée Payment, quelles définitions sont autoritatives ni quelles règles de rétention s’appliquent.

Quelle action est la meilleure ?

A. Compléter la Data Architecture : entities, ownership, lifecycle, quality, flows, governance et requirements, puis laisser les choix technologiques détaillés être traités au niveau approprié.  
B. Valider PostgreSQL comme Data Architecture complète.  
C. Reporter ownership et retention à Phase G.  
D. Supprimer la Data Architecture et traiter toutes les données dans l’Application Architecture.

**Scoring : A=5, B=3, C=1, D=0.**

**Pourquoi A :** Data Architecture traite l’information et sa gouvernance, pas seulement le moteur de base. B couvre un moyen technique mais pas le domaine ; C reporte des requirements structurants ; D efface une distinction importante.

**Mapping : Architecture Development — Phase C Data.**

## S025 — Application Architecture pilotée par un produit

Une équipe propose un progiciel de paiement avant d’avoir décrit les services applicatifs nécessaires, les interactions, les responsabilités de systèmes et les gaps.

Quelle approche est la meilleure ?

A. Développer d’abord la Target Application Architecture et ses requirements, puis évaluer le progiciel comme réalisation potentielle de building blocks.  
B. Acheter le progiciel et modifier la Target pour correspondre exactement au produit.  
C. Rejeter automatiquement le progiciel parce que TOGAF interdit les COTS.  
D. Définir uniquement les serveurs du progiciel en Phase C.

**Scoring : A=5, B=3, C=1, D=0.**

**Pourquoi A :** l’architecture doit garder la logique capability/service/requirement avant la sélection de solution. B peut être pragmatique mais devient vendor-driven ; C invente une interdiction ; D relève de Technology et reste incomplet.

**Mapping : Architecture Development — Phase C Application / ABB vs SBB.**

## S026 — Phase D sans lien avec B/C

L’équipe infrastructure définit une Target Technology Architecture standard, mais elle ne prend pas en compte les exigences de latence, résilience et event streaming identifiées en B/C.

Quelle action est la meilleure ?

A. Reconnecter Phase D aux requirements et building blocks issus de B/C, puis ajuster la Target Technology Architecture et les gaps.  
B. Conserver la cible standard : la technologie doit être indépendante des besoins métier.  
C. Réécrire les besoins métier pour s’adapter à l’infrastructure existante.  
D. Passer à Phase F et traiter l’écart comme un problème de planning.

**Scoring : A=5, B=3, C=1, D=0.**

**Pourquoi A :** les domaines sont distincts mais interdépendants. B valorise la standardisation mais ignore les requirements ; C inverse l’alignement ; D transforme un problème de Target Architecture en problème de migration.

**Mapping : Architecture Development — Phase D / Cross-Domain Alignment.**

## S027 — Un gap traverse plusieurs domaines

La Phase B révèle que MayaBank doit traiter les exceptions de paiement en temps réel. Cela exige de nouvelles données d’état, un service applicatif dédié et une plateforme capable de diffuser des événements.

Quelle action est la meilleure ?

A. Tracer le gap métier et ses impacts vers Data, Application et Technology Architecture, puis consolider les gaps avant Phase E.  
B. Classer le gap uniquement comme « Business » et interdire aux autres domaines de le traiter.  
C. Transformer immédiatement le gap en projet financé sans analyser les autres domaines.  
D. Attendre Phase H.

**Scoring : A=5, C=3, B=1, D=0.**

**Pourquoi A :** un gap métier peut avoir des conséquences transverses. C reconnaît l’action mais saute l’architecture nécessaire ; B cloisonne artificiellement ; D est très tardif.

**Mapping : Architecture Development — Gap Analysis across B/C/D.**

## S028 — Data et Application s’influencent

Pendant Phase C, la définition des événements métier modifie les frontières de services applicatifs ; ces nouvelles frontières révèlent à leur tour de nouveaux besoins de données. Le chef de projet interdit tout retour en arrière car « Data doit être terminée avant Application ».

Quelle action est la meilleure ?

A. Autoriser une itération contrôlée entre Data et Application Architecture jusqu’à obtenir une cohérence suffisante avec les requirements.  
B. Interdire toute itération et figer Data.  
C. Fusionner définitivement Data et Application en un seul domaine TOGAF.  
D. Reporter la résolution à Phase G.

**Scoring : A=5, B=3, C=1, D=0.**

**Pourquoi A :** l’ADM permet l’itération. B donne une discipline de séquence mais peut produire une incohérence ; C efface deux domaines distincts ; D reporte un problème de conception.

**Mapping : Architecture Development — Iteration within Phase C.**

## S029 — Quelle vue pour le métier ?

Le directeur Payments veut comprendre quelles capabilities et services métier changent. L’architecte lui propose une topologie réseau détaillée parce qu’elle est « techniquement complète ».

Quelle action est la meilleure ?

A. Sélectionner un viewpoint adapté aux concerns du directeur et produire une view orientée capabilities/services et impacts métier.  
B. Garder la topologie réseau et ajouter plus de détails.  
C. Ne produire aucune view car le directeur n’est pas architecte.  
D. Lui envoyer uniquement le catalogue de serveurs.

**Scoring : A=5, B=3, D=1, C=0.**

**Pourquoi A :** views et viewpoints répondent aux concerns. B conserve une représentation non adaptée ; D reste technique ; C exclut un stakeholder important.

**Mapping : Architecture Development — Stakeholders / Views.**

## S030 — Requirement découverte en Phase D

En Phase D, l’équipe découvre une exigence réglementaire imposant une localisation particulière de certaines données. Cela remet en cause une partie de Data Architecture et de Technology Architecture.

Quelle action est la meilleure ?

A. Enregistrer et évaluer la requirement via Requirements Management, puis itérer sur les domaines impactés et mettre à jour les artifacts/gaps.  
B. Ignorer la requirement parce que Phase C est déjà terminée.  
C. Continuer jusqu’à Phase G et demander une exception automatiquement.  
D. Modifier seulement le diagramme réseau sans tracer l’exigence.

**Scoring : A=5, D=3, C=1, B=0.**

**Pourquoi A :** Requirements Management est transversal et l’ADM supporte l’itération. D traite un impact mais sans traçabilité ni analyse Data ; C suppose l’exception avant analyse ; B est incompatible avec la gestion des exigences.

**Mapping : Architecture Development — Requirements Management / Iteration.**
